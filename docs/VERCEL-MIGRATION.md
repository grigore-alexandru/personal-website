# Netlify → Vercel migration

A four-step runbook for moving `alexandrugrigore.com` from Netlify to Vercel
without losing a single feature, a single SEO tag, or a single minute of uptime.

**Read the whole document once before doing anything.** Every step tells you
exactly what to click. Where a step can go wrong, it says how you will know and
what to do about it.

## The one hard problem, and how it was solved

Every social card on this site is generated by `ogImage()`, which used to send
the image through **Netlify's Image CDN**:

```
/.netlify/images?url=…&w=1200&h=630&fit=cover&position=center&fm=jpg&q=75
```

Those parameters are load-bearing. They exist because of three defects that
shipped to production once already: posters stored at 480px (too small for a
large card), every derivative stored as WebP (which WhatsApp renders
unreliably), and `og:image:width/height` hardcoded to 1200×630 on images that
were never that size.

**Vercel's image optimizer cannot do this.** `/_vercel/image` accepts exactly
three parameters — `url`, `w`, `q`. No crop, no aspect ratio, no format forcing.
Swapping one for the other would have silently reintroduced all three defects,
and the failure is invisible in a browser: the HTML looks perfect, and only
Facebook and WhatsApp show a broken card.

So `/og` was written to do precisely what the Netlify transform did. It was
checked against the live Netlify output on the same source image:

|  | Netlify (live today) | `/og` (new) |
|---|---|---|
| Dimensions | 1200×630 | 1200×630 |
| Format | progressive JPEG | progressive JPEG |
| Size | 146,622 bytes | 122,444 bytes |
| EXIF | retained | stripped |

Smaller, and it no longer leaks camera GPS data into a public social card.

> **One subtlety that matters:** the route is `/og`, **not** `/api/og`.
> `robots.ts` disallows `/api/` for every user agent, and Meta's scrapers apply
> robots.txt to the og:image fetch as well as to the page. Putting it under
> `/api/` would have produced blank previews with flawless HTML — the identical
> failure mode this project already hit once with the `/r/` disallow.

# STEP 1 — Create the Vercel project

**Nothing here affects your live site.** `alexandrugrigore.com` keeps serving
from Netlify throughout Steps 1 and 2.

### 1.1 Push the branch

In your terminal:

```bash
git push origin dev
```

### 1.2 Import the repository

1. Go to **https://vercel.com/new**
2. Sign in with the GitHub account that owns `grigore-alexandru/personal-website`.
3. Find **personal-website** in the list and click **Import**.
   - If it is not listed, click **Adjust GitHub App Permissions** and grant
     Vercel access to that repository.
4. On the configuration screen:
   - **Framework Preset** — should already say `Next.js`. If not, select it.
   - **Root Directory** — leave as `./`
   - **Build Command / Output Directory / Install Command** — leave all on
     default. `vercel.json` handles what needs handling.
5. **Do not click Deploy yet.** Expand **Environment Variables** first — see 1.3.

### 1.3 Environment variables — all ten

Still on the import screen, add each of these. **Take the values from your
Netlify dashboard**, not from your local `.env` file: Netlify is what production
is actually running, and a local file can have drifted.

Open a second tab: **Netlify → your site → Site configuration → Environment
variables**, and copy across one at a time.

| Name | Notes |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Public. Safe to expose. |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Public by design; RLS protects the data. |
| `NEXT_PUBLIC_MEGA_S4_ENDPOINT` | Public. |
| `NEXT_PUBLIC_MEGA_S4_ACCOUNT_ID` | Public. |
| `MEGA_S4_ENDPOINT` | Server only. |
| `MEGA_S4_ACCOUNT_ID` | Server only. |
| `MEGA_S4_ACCESS_KEY` | **Secret.** Never prefix with `NEXT_PUBLIC_`. |
| `MEGA_S4_SECRET_KEY` | **Secret.** Never prefix with `NEXT_PUBLIC_`. |
| `REVALIDATE_SECRET` | **Secret. Must match byte-for-byte** — see the warning below. |
| `LINK_HASH_SALT` | **Secret.** If missing, unique-visitor counts on short links silently become null. |

For **every** variable, tick all three environment boxes: **Production**,
**Preview**, **Development**.

> ### ⚠️ `REVALIDATE_SECRET` — the one that will bite you
>
> Your Supabase database has a trigger, `trigger_revalidate()`, that fires on
> every insert/update/delete in `posts`, `projects`, `content` and `documents`.
> It POSTs to `https://alexandrugrigore.com/api/revalidate` with a hardcoded
> `Authorization: Bearer <token>` header.
>
> **Good news:** it points at your *domain*, not at a Netlify URL. The moment
> DNS moves, it keeps working with zero database changes.
>
> **The catch:** if `REVALIDATE_SECRET` on Vercel does not exactly equal that
> hardcoded token, every request returns `401` and *your site stops updating when
> you edit content in the admin panel*. The pages will not error — they will just
> silently serve stale content forever, which is much harder to notice.
>
> Copy it from Netlify with no leading or trailing space.

`MEGA_S4_REGION` is **not** required — the code defaults to `eu-central-1`,
which is correct. Add it only if Netlify has it set to something different.

### 1.4 Deploy

Click **Deploy**. First build takes roughly 2–4 minutes.

**If the build fails**, open the build log and look at the first red line:

| Error mentions | Fix |
|---|---|
| `supabaseUrl is required` / `Invalid URL` | A `NEXT_PUBLIC_SUPABASE_*` variable is missing or misspelled. Settings → Environment Variables, then **Redeploy**. |
| `sharp` / `Module not found` | Deployments → ⋯ → Redeploy with **Use existing Build Cache unchecked**. |
| `ENOENT … pdf.worker.min.mjs` | The `postinstall` script did not run. Settings → General → Install Command → set to `npm install`. |

### 1.5 Set the function region — do not skip this

1. **Settings → Functions**
2. **Function Region** → select **Frankfurt, Germany (fra1)**
3. Save.

Your Supabase database is in `eu-central-1` (Frankfurt). Vercel's default region
is Washington D.C. Left on the default, every page render and every short-link
click crosses the Atlantic twice — roughly +200ms per database query, on the hot
path of a human clicking a link. `vercel.json` already requests `fra1`; setting
it in the dashboard too makes certain it applies.

### 1.6 Set the production branch

1. **Settings → Git**
2. **Production Branch** → confirm it is **`main`** (not `dev`).

This matters: it is what keeps `dev` pushes as previews instead of publishing
them to your live domain.

# STEP 2 — Verify everything on the preview URL

**Still nothing affecting your live site.** Vercel gave your project a URL like
`personal-website-xxxx.vercel.app` — find it at the top of the project page.

Do not skip this step. It is far cheaper to find a problem now than after DNS
has moved.

### 2.1 Turn off Deployment Protection first

1. **Settings → Deployment Protection**
2. Set **Vercel Authentication** to **Disabled** (or "Only Preview Deployments").

If this is left on for production, your live site will serve a Vercel login wall
to Google and to every visitor. It is the single most common way a Vercel
migration goes wrong.

### 2.2 Click through the site by hand

On the `.vercel.app` URL, check each of these:

- [ ] Homepage loads, images appear
- [ ] `/portfolio/projects` — grid loads, thumbnails sharp, click into a project
- [ ] `/portfolio/content` — grid loads; click an item, the **modal** opens
- [ ] `/blog` and one full blog post — hero image, rich text, images inside the body
- [ ] `/documents/cv-1` — the **PDF viewer renders** (this exercises the
      `pdf.worker.min.mjs` postinstall step; a blank box means it failed)
- [ ] `/contact`
- [ ] `/sitemap.xml` — lists your posts, projects, content and documents
- [ ] `/robots.txt`

### 2.3 Check the admin panel

- [ ] `/admin` redirects you to `/admin/login` when logged out
      *(this proves `middleware.ts` is running on Vercel's edge)*
- [ ] You can log in
- [ ] **Upload a test image** in the portfolio admin
      *(this proves the presigned-URL route and Mega S4 both work)*
- [ ] Delete the test image

> If the upload fails with a **CORS** error in the browser console, your Mega S4
> bucket only allows `alexandrugrigore.com` as an origin. That is fine and
> expected — it will work once you are on the real domain. Either add the
> `.vercel.app` origin to the bucket's CORS policy temporarily, or accept it and
> re-test uploads after Step 3.

### 2.4 Check the social cards — the important one

Replace `YOUR-PREVIEW-URL` with your actual `.vercel.app` hostname:

```bash
node scripts/check-crawler-access.mjs https://YOUR-PREVIEW-URL
```

Expect: `✓ all 5 paths serve complete metadata to every crawler`.

If it reports **HTTP 401** on every path, Deployment Protection is still on — go
back to 2.1.

Then verify a card image is really produced. Open a blog post's page source
(`Ctrl+U`), find the `og:image` URL, and paste it into your browser. You should
see a **1200×630 photo**, not the generic default card.

> Note: on the preview URL, `og:image` still points at
> `https://alexandrugrigore.com/og?...` — that is correct and intentional.
> `SITE_URL` is hardcoded to the production domain so that canonical tags never
> point at a preview. It means the card image you see there is being served by
> **Netlify** until Step 3. To test the *new* route specifically, take the
> `?url=…` part and put it on the preview host:
> `https://YOUR-PREVIEW-URL/og?url=<same encoded url>`

### 2.5 Tell Supabase about the new URL

**Supabase Dashboard → Authentication → URL Configuration → Redirect URLs** →
add:

```
https://YOUR-PREVIEW-URL/**
```

Leave `https://alexandrugrigore.com/**` in place. Without this, admin login on
the preview URL can fail to complete.

# STEP 3 — The DNS cutover

Only start this once Step 2 is fully green. This is the step with real-world
consequences.

### What is actually happening

Your domain is registered at **Namecheap**, but its nameservers currently point
at **Netlify's DNS** (`dns1.p06.nsone.net` … `dns4`). Netlify, not Namecheap, is
answering DNS queries for your domain today. So you are not changing a record —
you are changing **who answers**.

I checked your live DNS. Your zone contains **only** the website records: there
are **no MX records, no TXT records, no CAA records, no subdomains**. Nothing
else is riding on this domain.

> **This means there is no email to break.** The address `hello@alexandrugrigore.com`
> on your contact page does not currently receive mail — there is no mail server
> configured for the domain. (It is marked as a TODO placeholder in the code.)
> If you ever *do* set up email, do it after this migration, in Vercel's DNS.

### 3.1 Add the domain to Vercel — before touching Namecheap

1. **Vercel → your project → Settings → Domains**
2. Type `alexandrugrigore.com` → **Add**
3. When asked, choose the option that also adds **`www.alexandrugrigore.com`
   redirecting to `alexandrugrigore.com`**. This matches your current behaviour
   exactly (`www` returns a `301` to the apex today).
4. Vercel will show **"Invalid Configuration"** with a set of nameservers:
   ```
   ns1.vercel-dns.com
   ns2.vercel-dns.com
   ```
   **This warning is expected.** It just means DNS has not moved yet.

**Write those two nameservers down.** Vercel occasionally issues different ones —
use exactly what *your* dashboard shows, not what is printed here.

Adding the domain now creates the complete DNS zone on Vercel's side *before*
anything switches. That is what makes this cutover safe: at no point does a
nameserver answer with an empty zone.

### 3.2 Record what Netlify has, just in case

**Netlify → Domains → alexandrugrigore.com → DNS records.** Screenshot the whole
list. You have five minutes of work here and it is your insurance policy.

### 3.3 Change the nameservers at Namecheap

1. Log in to **https://namecheap.com**
2. **Domain List** → find `alexandrugrigore.com` → **Manage**
3. Find the **NAMESERVERS** section. It currently reads **Custom DNS** with the
   four `nsone.net` entries.
4. Keep it on **Custom DNS**, then **delete all four** `nsone.net` rows and enter
   the two Vercel ones:
   ```
   ns1.vercel-dns.com
   ns2.vercel-dns.com
   ```
5. Click the **green tick** to save. *(Namecheap does not save until you click
   it — this is the single most commonly missed click on the whole site.)*

### 3.4 Wait

Propagation typically takes **15–60 minutes**, occasionally up to 24 hours.
During the wait, some visitors reach Netlify and some reach Vercel. **Both serve
the same working site**, so there is no outage — this is exactly why Step 2
mattered.

Watch it with:

```bash
dig NS alexandrugrigore.com +short
```

When that prints the `vercel-dns.com` names instead of `nsone.net`, you are
through. Then check the certificate:

**Vercel → Settings → Domains** — you want a green **Valid Configuration** and a
issued SSL certificate. Vercel does this automatically within a few minutes of
the nameservers resolving.

> ### ⚠️ Do not panic about HTTPS during the wait
> Your site sends `Strict-Transport-Security: max-age=31536000`. Every browser
> that has ever visited will **refuse** to load the site over plain HTTP for a
> year. That is normally a good thing, but it means that between DNS resolving
> and Vercel's certificate being issued, you may briefly see a certificate
> warning. It resolves itself. **Do not** remove the domain from Vercel and
> re-add it — that restarts the certificate process from zero.

# STEP 4 — Verify, then decommission

### 4.1 Confirm you are actually on Vercel

```bash
curl -sI https://alexandrugrigore.com | grep -i "server\|x-vercel"
```

You want to see `x-vercel-id` and no `server: Netlify`.

### 4.2 Run the automated checks

```bash
npm run check:crawlers
```

Expect `✓ all 5 paths serve complete metadata to every crawler`.

### 4.3 Confirm the social cards for real

This is the check that actually matters, because it is the one that broke
before and is invisible everywhere else.

1. **Facebook Sharing Debugger** — https://developers.facebook.com/tools/debug/
   - Paste a blog post URL → **Scrape Again**
   - You want a **1200×630 photo**, not the generic card and not a blank box
2. **Send the link to yourself on WhatsApp.** This is the real test — WhatsApp
   is the client that was broken before.
3. Repeat with a **short link** (`/r/<slug>`) — it should show the destination's
   card, not a generic one.

> WhatsApp and Facebook cache aggressively. If a card looks stale, "Scrape Again"
> in the debugger clears Meta's cache for that URL.

### 4.4 Confirm on-demand revalidation works

The single most valuable end-to-end test, because it exercises Supabase →
Vercel → cache in one go:

1. Open `/admin/blog`, edit a post's title, save.
2. Wait ~10 seconds.
3. Open that post's public page in a **private/incognito window**.
4. **The new title should be there.**

If it is not, `REVALIDATE_SECRET` does not match. Check
**Vercel → Deployments → the latest one → Runtime Logs**, filter for
`/api/revalidate`, and look for `401`.

### 4.5 Tidy up Supabase

**Supabase → Authentication → URL Configuration**

- **Site URL** — confirm it is `https://alexandrugrigore.com`
- **Redirect URLs** — you may now remove the `.vercel.app` preview entry you
  added in 2.5, or keep it if you want to test admin login on previews.

### 4.6 Google Search Console

Nothing to re-verify — your verification is almost certainly a file or meta tag
served by the site itself, which moved with it. But do:

1. **Sitemaps** → resubmit `https://alexandrugrigore.com/sitemap.xml`
2. **URL Inspection** → test the homepage → **Live Test** → confirm Google
   fetches it successfully.

Your URLs, canonicals, redirects and structured data are all unchanged, so there
is **no ranking impact** from this migration. The two `/what-i-do/video-production`
permanent redirects live in `next.config.js` and moved with the code.

### 4.7 Wait two weeks, then turn Netlify off

**Do not delete the Netlify site immediately.** Leave it running for ~2 weeks as
a rollback path (see below). Then:

1. Netlify → Site configuration → **Delete site**
2. Remove the domain from your Netlify team so it stops appearing in their DNS.

## Rollback

If something is badly wrong after cutover, you are not stuck.

**Fastest (minutes) — stay on Vercel, serve from Netlify:**
Vercel now controls your DNS zone, so you can point the domain back at Netlify
from inside Vercel:

1. **Vercel → Settings → Domains → alexandrugrigore.com → DNS Records**
2. Change the apex `A` record to Netlify's load balancer: `75.2.60.5`
3. Change `www` to a `CNAME` pointing at `sweet-vacherin-65bc21.netlify.app`

Vercel's DNS TTLs are low, so this takes effect in minutes. This is the main
reason Vercel nameservers were the right choice over Namecheap DNS.

**Full revert (slow):** change the nameservers at Namecheap back to the four
`nsone.net` entries. Correct, but propagation means hours.

**Rolling back a bad deploy** (not a DNS problem): Vercel → Deployments → find
the last good one → ⋯ → **Promote to Production**. Instant, no rebuild.

## Things that will *not* need changing — and why

Worth knowing so you do not go hunting for problems that do not exist.

| Thing | Status |
|---|---|
| **Supabase revalidation webhook** | Points at your domain, not a Netlify URL. Works untouched. |
| **URLs, canonicals, redirects, JSON-LD** | All generated by Next.js from your code. Identical output. |
| **`middleware.ts` admin protection** | Runs on Vercel's edge, same as Netlify's. No change. |
| **ISR / `revalidatePath`** | Native Next.js. Vercel implements it directly — better supported here than on Netlify. |
| **Mega S4 direct uploads** | Browser → S4 directly. Vercel only signs the URL. Unaffected. |
| **Netlify Forms** | Enabled on your Netlify project but **not used anywhere in the code**. Nothing to migrate. |
| **`_redirects` / `_headers` files** | You have none. All redirects are in `next.config.js`. |
| **Netlify Edge Functions** | You have none. |
